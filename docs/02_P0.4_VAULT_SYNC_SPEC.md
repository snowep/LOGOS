# LOGOS — P0.4 Reliable Vault Synchronization Specification

## Goal

P0.4 is not merely “Chokidar + SSE”.

P0.4 is:

> **Reliable Vault ↔ LOGOS State Synchronization**

The system must maintain trustworthy awareness of meaningful Markdown documents while protecting data integrity.

---

## 1. Canonical Flow: Vault → LOGOS

```text
Markdown file changes
        ↓
Watcher receives event
        ↓
Normalize path
        ↓
Resolve document identity
        ↓
Read current file metadata/content when needed
        ↓
Compute version/hash
        ↓
Compare with known state
        ↓
Persist document state
        ↓
Persist document event
        ↓
Update retrieval/index metadata
        ↓
Evaluate whether information deserves memory
        ↓
Notify UI
```

---

## 2. Canonical Flow: LOGOS → Vault

```text
User request
        ↓
LOGOS plans change
        ↓
Relevant context is gathered
        ↓
Proposed modifications are prepared
        ↓
User approval when required
        ↓
Current document version checked
        ↓
Atomic write
        ↓
Post-write verification
        ↓
Document state updated
        ↓
Event emitted
        ↓
Result reported
```

---

## 3. Document Event Types

At minimum:

```text
created
modified
deleted
renamed
moved
```

The implementation may map filesystem-level events to these semantic events.

---

## 4. Document Metadata

Minimum useful metadata:

```text
document_id
path
version
hash
size
created_at
updated_at
last_writer
last_event_type
```

Additional metadata may include:

```text
mime/type
frontmatter metadata
project association
knowledge type
```

---

## 5. Hashing

Use a strong deterministic content hash suitable for integrity/version comparison.

Do not use a tiny ad-hoc integer hash as the authoritative conflict detector.

The hash must be stable and practical to compute locally.

---

## 6. Rename and Move

A rename should preserve document identity.

Example:

```text
before:
Document ID = D1
path = projects/drop-002.md

rename:
projects/drop-002.md
→ projects/drop-002-final.md

after:
Document ID = D1
path = projects/drop-002-final.md
```

Do not create a new logical document merely because the path changed.

---

## 7. Conflict Semantics

A conflict exists when a planned write is based on stale state.

Example:

```text
LOGOS reads version 7 / hash A
LOGOS prepares edit
user changes file
file becomes version 8 / hash B
LOGOS attempts version-7 write
→ conflict
```

A normal sequence of user edits is not automatically a conflict.

---

## 8. Self-Generated Events

LOGOS must recognize changes it caused itself.

A file write should carry enough metadata for the watcher/index layer to associate the resulting filesystem event with the originating writer/operation.

This prevents endless loops such as:

```text
LOGOS writes
→ watcher sees change
→ LOGOS interprets it as external change
→ LOGOS writes again
→ loop
```

---

## 9. Memory Promotion

P0.4 should record file events but should not pretend that every change is useful memory.

Examples:

### Likely durable information

```text
DROP 002 release quantity changed from 11 to 22.
```

### Likely event-only information

```text
paragraph wording edited
```

The memory evaluator may later promote important facts, decisions, preferences, or experiences.

---

## 10. UI Notification Contract

The normal UI should receive concise information:

```text
DROP 002.md was updated.
```

or:

```text
2 project notes changed.
```

For conflicts:

```text
LOGOS found a conflicting change in DROP 002.md.
Review before applying the pending update.
```

Do not force raw hashes or filesystem paths into the main UI.

---

## 11. SSE Contract

SSE should be an event notification channel.

Do not transmit full file contents by default.

Example event:

```json
{
  "documentId": "doc_123",
  "event": "modified",
  "path": "projects/drop-002.md",
  "version": 8,
  "hash": "...",
  "writer": "USER",
  "timestamp": "..."
}
```

---

## 12. Manual Reconciliation

`Sync Now` should perform a filesystem/database reconciliation.

Conceptual algorithm:

```text
scan intended vault Markdown files
        ↓
resolve identities
        ↓
compare filesystem state to indexed state
        ↓
classify created/modified/deleted/renamed
        ↓
update state
        ↓
record events
        ↓
report actual reconciliation summary
```

Example result:

```text
Sync complete

3 updated
1 created
0 deleted
1 conflict
```

---

## 13. P0.4 Completion Criteria

P0.4 is complete only when:

- user file edits are detected reliably;
- LOGOS writes are detected correctly;
- renames preserve identity;
- conflicts are based on stale state rather than timing alone;
- file events are persistent;
- event payloads are lightweight;
- manual reconciliation is real;
- no infinite watcher loops occur;
- no full-file event flooding occurs;
- memory is not polluted by every edit;
- synchronization results are verifiable;
- tests cover normal edits, rapid edits, delete, rename, self-write, stale-write conflict, and reconnect cases.
